Coupling design

The SUMMA--mizuRoute integration supports two different workflows for combining land-surface simulations with river-network routing:

  • Sequential: SUMMA and mizuRoute are run as separate executables. SUMMA first generates runoff, which is subsequently provided as input to a standalone mizuRoute simulation.
  • Coupled: mizuRoute is linked directly with SUMMA and river routing is performed during the SUMMA simulation.

The sequential workflow remains useful when land-surface and river-routing simulations can be performed independently. The coupled workflow allows information to be exchanged between the land and river components during model execution. This capability is needed for applications such as streamflow data assimilation and, more generally, coupling between terrestrial and river processes.

Design philosophy

The SUMMA--mizuRoute integration was designed around a simple principle: mizuRoute provides river-network routing capabilities, while the host land model controls the overall coupled simulation.

In a standalone mizuRoute simulation, mizuRoute manages the complete routing workflow. It reads runoff generated by a land model, initializes the river network, manages its parallel execution, performs river-network routing, and writes the resulting streamflow and other routing variables to its own output files.

In a coupled simulation, these responsibilities are deliberately divided between mizuRoute and the host land model. The host model manages the overall simulation, including the model driver, data exchange, and I/O. mizuRoute provides the specialized capabilities needed to initialize the river network and perform the routing calculations.

The coupled implementation therefore separates these routing capabilities from the infrastructure used to run mizuRoute as a standalone model. Initialization and river-network routing are exposed as distinct operations that can be invoked by the host model. The host model determines when these operations are performed, supplies the required runoff and other information, and manages the resulting routed quantities within its own simulation framework.

For SUMMA, this means that SUMMA retains control of its model driver, data structures, and NetCDF I/O, while mizuRoute remains responsible for constructing the river network and performing the river-routing calculations. This avoids requiring SUMMA to adopt the execution and I/O infrastructure of the standalone mizuRoute model.

This design is intended to make mizuRoute a reusable routing component rather than a routing system tied specifically to SUMMA. Other land surface or hydrologic models can adopt the same pattern: the host model manages the coupled simulation and calls a small number of mizuRoute operations to initialize and route the river network. The SUMMA implementation therefore provides one example of a more general coupling strategy rather than a SUMMA-specific design.

Parallel execution

The intended parallel design described above has not yet been implemented in the current SUMMA--mizuRoute coupling. At present, the coupled configuration does not support parallel execution of the coupled land--river system.

SUMMA has an existing domain-parallel implementation in which the land-model domain is divided into spatial chunks that can be simulated independently. This strategy works because the land calculations in different domain partitions do not normally require exchange of model states between partitions.

River-network routing introduces a fundamentally different dependency structure. Flow generated in one part of the domain must be propagated downstream through the connected river network. Upstream and downstream reaches can occur in different SUMMA domain partitions, so those partitions can no longer be advanced independently. The existing SUMMA domain decomposition therefore cannot simply be applied to the coupled land--river system.

The long-term design is for the host model to extend its parallel execution strategy to account explicitly for river-network connectivity. The host model would coordinate the exchange of information across domain partitions while mizuRoute would continue to provide the network topology and routing calculations. This preserves the broader design principle that the host model controls execution of the coupled system rather than requiring it to adopt the parallel execution infrastructure of the standalone mizuRoute model.

Developing this capability requires a decomposition and communication strategy that respects both the land-model partitioning and dependencies along the river network. Parallelization of the coupled SUMMA--mizuRoute system therefore remains future work.

Until this capability is implemented, users who require the parallel routing capabilities currently available in mizuRoute should use the sequential workflow: first run SUMMA to generate runoff and then run the standalone mizuRoute executable using its native parallel implementation.

Software independence and portability

An important objective of the coupling design is to preserve the independence of SUMMA and mizuRoute. Both models remain usable as standalone modeling systems, and coupling should not require either model to incorporate the internal implementation details of the other.

mizuRoute is included in SUMMA as a Git submodule, allowing SUMMA to use a specific upstream mizuRoute release while maintaining a clear boundary between the two codebases. The current implementation is tied to mizuRoute v3.1.1, and no source files within that Git submodule have been modified for the SUMMA coupling. All SUMMA-specific integration code is maintained outside the mizuRoute submodule.

The coupling is deliberately restricted to a small number of exchanges between the host model and mizuRoute. Keeping this interface narrow reduces dependencies between the two codebases and makes it easier for each model to evolve independently.

This separation is also important for portability. A coupling architecture that depends extensively on SUMMA data structures, execution logic, or I/O would be difficult to reproduce in another land model. In contrast, an interface based on a small number of initialization, data-exchange, and routing operations can be implemented by another host model with relatively little modification.

The goal is therefore not simply to couple mizuRoute to SUMMA, but to establish a pattern in which mizuRoute can provide river-routing capabilities to different host modeling systems while allowing each host model to retain control of its own simulation infrastructure.

The technical implementation of this design, including the thin interface layer, compatibility shims, coupling points, and management of source dependencies in CMake, is described in Coupling architecture.
